Plan: 2026-11-02-post-incident-memory-extractor.md (revision 1). Revision 2 of the plan answers every [high] item.

Reviewed both plans, `CLAUDE.md`, all `.claude/rules/*.md`, and the affected implementation at `bf60ffc` on `feat/gateway-knowledge-tools`. The draft targets its parent, `2248eb4`. No files were modified; this was a static review.

The main blockers are outcome attribution, atomic memory protection, and extraction lifecycle consistency.

## 1. Factual errors

- **[high] The run-level field is `outcome`, not `result_status`.** D3’s outcome table references “newest run `result_status`.” `AgentRun.Outcome` already stores the parsed result; `Incident.ResultStatus` is a separate incident-level value. They are not interchangeable: the incident value is only updated when the new parsed outcome is nonempty, so it can retain an earlier run’s verdict. Use the selected run’s `Outcome`. Sources: [models_agent_runs.go:72](internal/database/models_agent_runs.go:72), [agent_ws.go:512](internal/handlers/agent_ws.go:512).

- **[high] `operator_closed` cannot be determined from a firing alert remaining after manual close.** `CloseIncident` resolves every remaining firing alert inside the transaction. By the time `Enqueue` reads the database, that evidence has disappeared. D3 needs a persisted pre-close observation or resolution provenance. Source: [incident_service.go:389](internal/services/incident_service.go:389).

- **[high] `session_export.jsonl` does not contain the incident’s successive runs.** Every run copies its session to the same `<scope>/session_export.jsonl`, overwriting the previous export. Follow-up turns reuse the scope and start fresh sessions. “Newest runs first” cannot be implemented from this file. Earlier runs’ DB logs must be included even when the export exists, or exports must become run-specific. Sources: [agent-runner.ts:990](agent-worker/src/agent-runner.ts:990), [.claude/rules/agent-runs.md:25](.claude/rules/agent-runs.md:25).

- **[medium] Retention does not currently behave as D3’s fallback assumes.** The incident cleanup query selects `completed`, `failed`, and `diagnosed`; it excludes `closed`, `monitor`, and `merged`. For incidents it does delete, it also deletes alerts and clears run `full_log`, `response`, and `session_id`. Thus “retention removed the export, so use the retained run payload” is not a reliable retention fallback. This is an existing lifecycle inconsistency, not a new extractor bug. Source: [retention_service.go:94](internal/services/retention_service.go:94), [retention_service.go:129](internal/services/retention_service.go:129).

- **[medium] Only stale close has the stated 500-item batch.** The monitor sweep closes all matching expired monitor incidents in one transaction and returns only a count. Step 3 cannot assume both sweep implementations already return a bounded UUID list. Sources: [stale_close_service.go:19](internal/services/stale_close_service.go:19), [monitor_sweep_service.go:47](internal/services/monitor_sweep_service.go:47).

- **[medium] Incident-thread operator requests are not guaranteed to become feedback memories.** The classifier can fail, be unavailable, or return a negative verdict. Its prompt explicitly excludes commands to do something now. D2’s assertion that operator asks “already reach memory through the feedback classifier” overstates this path; blocking incident-run writes can leave an explicit “remember” request unfulfilled. Sources: [slack_feedback.go:79](internal/handlers/slack_feedback.go:79), [feedback_classifier.go:118](internal/services/feedback_classifier.go:118).

- **[low] Several implementation references need correction.** There is no incident `closed_at`; close paths use `resolved_at`. The gateway write guard is `requireRun`, not `runForWrite`, and advertised knowledge-tool schemas live in `registry_knowledge.go`. Sources: [models_incidents.go:63](internal/database/models_incidents.go:63), [tool.go:466](mcp-gateway/internal/tools/knowledge/tool.go:466), [registry_knowledge.go:89](mcp-gateway/internal/tools/registry_knowledge.go:89).

## 2. Design risks

- **[high] The proposed classifier can manufacture “verified” causes from administrative closure.** Manual close and monitor sweep both stamp unresolved alerts with the current time. A run reporting `resolved`, followed by either operation, can satisfy `resolved_after_agent` without any independently observed recovery. Stale close also fabricates resolution timestamps, and its outcome overlaps `self_resolved` unless close-reason precedence is explicit. Record whether resolution came from the source, an operator, or a sweep; administrative timestamps must never verify remediation. Sources: [incident_service.go:399](internal/services/incident_service.go:399), [monitor_sweep_service.go:52](internal/services/monitor_sweep_service.go:52), [stale_close_service.go:235](internal/services/stale_close_service.go:235).

- **[high] Completion time is the wrong boundary for attributing remediation.** A real fix can clear the alert while the agent is still investigating; the plan labels that `self_resolved`. Conversely, an inaccurate `resolved` answer followed by an unrelated recovery qualifies for verification. Source-reported clears are stored using receipt time, further weakening this comparison. Require an identified action and evidence associated with that action, or retain `hypothesis`. Sources: [alert_processor.go:410](internal/handlers/alert_processor.go:410), [alert_processor.go:450](internal/handlers/alert_processor.go:450), [models_agent_runs.go:196](internal/database/models_agent_runs.go:196).

- **[high] Closing does not guarantee that the investigation has stopped or that its inputs remain stable.** Manual close permits confirmed closure of running incidents. It does not finish/cancel the run, and subsequent `completeIncident` writes a new status without rejecting an already-closed incident. A Slack follow-up also sets the incident running again. Extraction can therefore race unfinished output, reopening, and later closes. Capture a closure generation and selected run IDs; revalidate them before committing memories. Sources: [incident_service.go:378](internal/services/incident_service.go:378), [incident_service.go:765](internal/services/incident_service.go:765), [incident_service.go:966](internal/services/incident_service.go:966).

- **[high] Enqueueing sweep candidates would extract incidents that did not close.** Stale close deliberately reapplies the activity predicate during its UPDATE; its original candidate list can include incidents that became active meanwhile. Both sweep interfaces currently return counts rather than the exact successful transitions. Capture the UUIDs actually transitioned within the transaction, preserving the existing recheck. Source: [stale_close_service.go:224](internal/services/stale_close_service.go:224); rule: [.claude/rules/alerts-correlation-and-monitor.md:129](.claude/rules/alerts-correlation-and-monitor.md:129).

- **[high] Merge separates the alert evidence from the run evidence.** The transaction moves all child alerts to the survivor but leaves the child’s runs under the child incident. Extracting the child after commit finds no linked alerts. Extracting the survivor later finds alerts investigated by runs outside its own scope. Two extractions can also miscount one merged outage as corroboration from independent incidents. Prefer extraction when the survivor closes, explicitly gathering the merge family’s runs and provenance. Source: [incident_merger.go:207](internal/services/incident_merger.go:207).

- **[high] D3’s proposed `UpsertByName` path does not enforce memory protection atomically.** The API upsert can replace an operator-owned or source-file memory’s content; preserving `created_by` does not protect the body. A prior ownership check races operator edits and proposal approval. The extractor needs an agent-specific conditional write with protection in the SQL statement, matching the gateway. Sources: [memory_service.go:966](internal/services/memory_service.go:966), [tool.go:597](mcp-gateway/internal/tools/knowledge/tool.go:597); rule: [.claude/rules/memory-and-runbooks.md:37](.claude/rules/memory-and-runbooks.md:37).

- **[high] Updating a memory from its manifest entry can erase existing knowledge.** D3 supplies names and descriptions, then permits replacement of the full body. The model never receives the existing body it must preserve. Meanwhile, API upsert replaces `incident_uuid`, losing earlier provenance. Read candidate bodies before generating replacements, use a revision check against concurrent Dreaming/operator changes, and retain multiple evidence sources. Sources: [memory_service.go:1195](internal/services/memory_service.go:1195), [memory_service.go:969](internal/services/memory_service.go:969).

- **[high] The job model permits lost work, duplicate memories, and misleading failure status.** A crash between close commit and `Enqueue` leaves no pending marker. Repeated enqueue/rerun requests are serialized, not deduplicated. A failure after saving some of five memories leaves partial output; rerunning `CreateWithUniqueName` can create suffixed duplicates. Existing memory methods can also report failure *after* the DB write succeeds because disk synchronization failed. Persist pending work with the close, claim it conditionally, and make output application idempotent and transactional. Sources: [context_summarizer.go:88](internal/services/context_summarizer.go:88), [memory_service.go:53](internal/services/memory_service.go:53), [memory_service.go:75](internal/services/memory_service.go:75).

- **[high] “Code-enforced grading” still trusts the model to choose the decisive facts.** The model supplies `claim`, `cause_at`, and `effect_at`. It can label a causal statement `factual`, producing `observed`, or invent ordered timestamps that produce `verified`. Request agents can likewise submit a causal claim with the default `observed` grade. Separate schema validation from evidence validation: require source references for observations and keep unsupported causal statements hypothetical. D1/D3’s current contract does not establish the advertised guarantee. Source: [the plan:70](docs/plans/2026-11-02-post-incident-memory-extractor.md:70).

- **[high] D6’s maintenance reads defeat its own decay rule.** Every `memory.get` increments recall, including Dreaming reading a legacy row to grade it. That row can then never satisfy `recall_count = 0`. Repeated reads also measure calls, not useful application, while manifest/search use is missed. If implemented with ordinary timestamp-updating GORM writes, reads additionally reorder manifests and change `since` pagination and refresh fingerprints. Exclude maintenance reads, define the counting unit, and update counters without changing content timestamps. Sources: [db.go:1040](internal/database/db.go:1040), [tool.go:315](mcp-gateway/internal/tools/knowledge/tool.go:315), [incident_service.go:819](internal/services/incident_service.go:819).

- **[medium] Dreaming cannot guarantee the proposed legacy grading and decay.** Its existing prompt restricts work to global memories updated within 14 days and exits when there are no duplicates. Appending jobs leaves those instructions conflicting with grading older rows and deleting 90-day-old rows. Skill-scoped memories never participate. Disabled jobs and preserved custom prompts may never perform the migration at all. Sources: [db.go:1038](internal/database/db.go:1038), [db.go:1163](internal/database/db.go:1163).

- **[medium] Shared prompt files cannot express the proposed incident/request distinction by blanket replacement.** Slack/API requests use the same `incident-manager` root; every run shares generated skill files. Replacing their write guidance with “Do not record memories” also tells allowed request runs to stop writing, and contradicts cron maintenance when those skills are read. Put incident-specific policy in run-specific context; make shared guidance conditional. Sources: [incident_service.go:670](internal/services/incident_service.go:670), [skill_prompt_service.go:174](internal/services/skill_prompt_service.go:174), [incident_service.go:909](internal/services/incident_service.go:909).

- **[high] Proposal staleness would ignore evidence changes.** Memory proposal snapshots and approval payloads currently contain only scope/type/name/description/body; staleness compares body, description, and type. An extractor or operator can change evidence while an old proposal remains approvable, after which approval defaults it to `verified`. Extend snapshot, draft, comparison, and apply contracts together, with explicit compatibility for old pending proposals. Source: [proposal_service.go:39](internal/services/proposal_service.go:39), [proposal_service.go:265](internal/services/proposal_service.go:265).

- **[medium] Authorship is being conflated with verification.** Slack feedback includes ambiguous facts and operator instructions; from-text creates an LLM draft without a separate confirmation step. Automatically calling all these `verified` conflicts with the recall definition “a cause confirmed by an outcome.” Context summaries can also quote hypotheses rather than direct observations. Keep ownership/protection separate from epistemic status, and define how mixed-claim memories are graded. Sources: [feedback_classifier.go:113](internal/services/feedback_classifier.go:113), [api_memories.go:230](internal/handlers/api_memories.go:230).

## 3. Gaps

- **[high] Contradiction handling has no implementable output contract.** D6 expects the extractor to mark an existing memory contradicted, but D3 emits only new/upserted memories and a timeline. It defines no contradicted target, evidence reference, or conditional mutation. Deleting based on prose in `evidence_note` also risks deleting a memory corrected after the note was produced. Use a typed contradiction record tied to a memory revision; initially flag it for review rather than deleting it. Source: [the plan:156](docs/plans/2026-11-02-post-incident-memory-extractor.md:156), [the plan:244](docs/plans/2026-11-02-post-incident-memory-extractor.md:244).

- **[high] Outcome precedence and eligibility need a complete decision table.** Decide behavior for zero alerts, no run, unfinished/failed/superseded newest runs, empty outcomes, mixed resolution timing, manual closure of merged incidents, and missing timestamps. Define whether failed incidents ever get extraction: automatic close deliberately excludes them. “Every alert resolved” must not become true evidence for an empty alert set. Source: [stale_close_service.go:75](internal/services/stale_close_service.go:75), [models_agent_runs.go:13](internal/database/models_agent_runs.go:13).

- **[medium] The mutation/default contract is incomplete.** Specify omitted versus explicit-null evidence, the default for `claim`, preservation or invalidation of existing grades on content changes, source-file versus operator precedence, and whether operators can clear notes. D6 requires writing `evidence_note`, but D2 only adds `evidence` and `claim` to the tool schema. Nullable columns also require NULL-aware upsert difference predicates; copying the current `<>` pattern will miss NULL-to-value-only changes. Sources: [registry_knowledge.go:90](mcp-gateway/internal/tools/registry_knowledge.go:90), [memory_service.go:969](internal/services/memory_service.go:969).

- **[medium] Corroboration needs durable provenance, not a 500-byte note.** The model has one `incident_uuid`, and upserts replace it. Neither that field nor free-text UUID lists reliably support “different incidents,” “seen in N incidents,” or “from one incident” after consolidation. Decide whether to retain source associations or defer corroboration/decay until they exist. Source: [models_context.go:60](internal/database/models_context.go:60).

- **[medium] Input reduction needs an evidence-preservation policy.** Define run-to-export matching, handling of user/operator turns, timestamps versus receipt times, and truncated/missing evidence. Large tool results already spill to `tool_outputs`; another 2 KiB cut can remove the metric samples needed for temporal ordering. Define total caps for alerts, feedback, manifests, and timeline output as well as transcript bytes. Any artifact reads need bounded, confined file access. Rule: [.claude/rules/agent-worker-pi-sdk.md:97](.claude/rules/agent-worker-pi-sdk.md:97).

- **[high] Gateway authorization must be preserved explicitly.** Add the incident refusal inside the existing validated-run path for both write and delete. Keep scope matching, finished-run rejection, proposal-run rejection, generation gating, and quotas. Checking only “incident UUID absent” would accidentally admit proposal chat. The extractor itself should use an internal protected persistence method, without inventing a running gateway identity for a closed incident. Source: [tool.go:464](mcp-gateway/internal/tools/knowledge/tool.go:464); rule: [.claude/rules/memory-and-runbooks.md:41](.claude/rules/memory-and-runbooks.md:41).

- **[medium] The endpoint, startup, gate, and retention contracts are missing.** Specify rerun responses for active/already-pending/merged/missing incidents, and whether rerun replaces prior extraction output. Decide whether turning generation off during a call prevents its later writes—the current rule checks each mutation. Initialize recovery before startup sweeps, and define what retention does to pending jobs and retained evidence. Sources: [cmd/akmatori/main.go:511](cmd/akmatori/main.go:511), [.claude/rules/memory-and-runbooks.md:79](.claude/rules/memory-and-runbooks.md:79).

- **[medium] The implementation/test inventory misses several necessary surfaces.** Include REST request DTOs and evidence filtering, proposal contracts, `SaveFileSummary`, gateway schema registration, startup wiring, OpenAPI, and export/frontmatter metadata. B2 is independent, so exports must preserve grades while mirrors exist. Add tests for close-before-enqueue crashes, partial saves, repeated reruns, concurrent operator ownership changes, merge-family extraction, maintenance recall exclusion, and NULL-only metadata updates. Sources: [api_memories.go:20](internal/handlers/api_memories.go:20), [memory_source_files.go:22](internal/services/memory_source_files.go:22), [memory_service.go:1111](internal/services/memory_service.go:1111).

- **[low] The external and deployment claims lack reproducible evidence.** I could not independently retrieve the cited Codex commit. Add repository/path links pinned to that revision before treating those details as verified precedent. The reported incident and “tens of incidents a day” workload also need a sanitized fixture or operational measurement; neither can be established from this repository. Source: [the plan:23](docs/plans/2026-11-02-post-incident-memory-extractor.md:23).

## 4. Answers to the four open questions

1. **[high] Trigger at close, with durable scheduling and stable inputs.** Avoid a second generative pass at completion. Capture run evidence at completion if necessary, then extract after a validated closure. For merges, wait for the survivor and include the merge family. Do not promise an approximately one-hour delay universally: unresolved alerts can hold incidents at `completed`, recurrence extends monitoring, and stale close defaults to three days. Sources: [incident_service.go:949](internal/services/incident_service.go:949), [.claude/rules/alerts-correlation-and-monitor.md:124](.claude/rules/alerts-correlation-and-monitor.md:124).

2. **[high] `resolved_after_agent` is too generous for `verified`.** Keep causal claims hypothetical unless an operator explicitly confirms the claim or a separately defined validation mechanism establishes it. Record “alert cleared after restart” as an observation with supporting evidence. Neither the agent’s self-report nor administrative alert resolution establishes causation. Also avoid promoting every operator-authored statement automatically. Sources: [models_incidents.go:91](internal/database/models_incidents.go:91), [monitor_sweep_service.go:52](internal/services/monitor_sweep_service.go:52).

3. **[medium] Prefer a deterministic conservative migration over reliance on Dreaming.** Between the offered choices, backfill legacy agent rows to `hypothesis`, explaining “legacy; evidence not assessed,” with explicit handling for file summaries. Better naming would be `unverified`, because not every legacy row is causal. Do not infer `claim=causal` from the grade. NULL is acceptable only if it permanently means unassessed and recall treats it cautiously; global-only, editable Dreaming cannot guarantee eventual grading. Sources: [db.go:1038](internal/database/db.go:1038), [db.go:1178](internal/database/db.go:1178).

4. **[medium] Keep `memory.write` available to Slack-mention request runs.** The feedback classifier requires existing thread work and deliberately rejects task commands, so it cannot replace request-run memory work reliably. Preserve existing auth, protection, quotas, and generation gating; keep agent causal writes hypothetical. An explicit operator request should not automatically grant verification to every statement the agent generates. Separately define a dependable incident-thread “remember” path. Sources: [slack_feedback.go:94](internal/handlers/slack_feedback.go:94), [feedback_classifier.go:118](internal/services/feedback_classifier.go:118), [tool.go:466](mcp-gateway/internal/tools/knowledge/tool.go:466).

## 5. Simplifications

- **[high] Cut automatic causal verification from the first version.** Use `observed` for supported observations and `hypothesis`/`unverified` for causal conclusions. This removes the fragile `resolved_after_agent` promotion rule while addressing the reported failure. Preserve the outcome as contextual evidence. Source: [the plan:78](docs/plans/2026-11-02-post-incident-memory-extractor.md:78).

- **[medium] Defer usage-driven decay and automatic contradiction deletion.** Neither is necessary to stop premature incident memories, and both require provenance, usage semantics, and concurrency rules absent from the draft. Ship non-destructive contradiction flags first. Source: [the plan:233](docs/plans/2026-11-02-post-incident-memory-extractor.md:233).

- **[medium] Initially create idempotent incident extraction records; leave cross-incident consolidation to one owner.** This avoids two independent systems rewriting the same memories from different snapshots. Existing Dreaming already owns consolidation; an extractor should only replace existing knowledge once it has read the body and can conditionally update its revision. Sources: [db.go:1031](internal/database/db.go:1031), [memory_service.go:155](internal/services/memory_service.go:155).

- **[medium] Centralize the successful-close scheduling contract.** Keep manual, monitor, and stale-close eligibility distinct, but have each persist the same extraction-pending transition and closure metadata. A single worker claims those rows after commit. This is simpler to recover and test than separate fire-and-forget hooks plus a reset-to-failed convention. Sources: [monitor_sweep_service.go:47](internal/services/monitor_sweep_service.go:47), [stale_close_service.go:232](internal/services/stale_close_service.go:232).

- **[low] Merge the seven delivery steps into three coherent changes.** First: evidence contracts across storage, API, gateway, proposals, and recall. Second: incident-write refusal plus durable extraction and lifecycle tests. Third: UI and optional maintenance enhancements. This reduces periods where grades exist but are invisible, or new fields disappear through older write surfaces. The one-shot service and interface boundaries already fit repository rules. Source: [CLAUDE.md:60](CLAUDE.md:60).
