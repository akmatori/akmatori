# pi SDK Upgrade 0.82.1 → 0.84.1

## Summary

Three releases to cross: **0.83.0**, **0.84.0**, **0.84.1**. There is no 0.82.2.

| Package | Current | Target |
|---|---|---|
| `@earendil-works/pi-coding-agent` | 0.82.1 | 0.84.1 |
| `@earendil-works/pi-ai` | 0.82.1 | 0.84.1 |
| `@earendil-works/pi-agent-core` | 0.82.1 | 0.84.1 |
| `pi-subagents` | 0.36.0 | 0.45.1 |

0.84.0 carries a large breaking-change list, but **almost none of it touches Akmatori** — most of it lands
on the TUI, the extension provider-refresh contract, and pi-agent-core's internal session harness, none of
which we drive. Verified against the 0.84.1 typings (`npm pack`, not assumption): `createAgentSession`,
`SessionManager.create/continueRecent/inMemory`, `ModelRuntime.registerProvider/getAuth`, and
`agent.onPayload` all survive unchanged.

Exactly **one compile-breaking call** exists in our code (`setRuntimeApiKey`'s third argument), plus one new
failure mode worth handling. The rest of the work is opt-in adoption.

Effort: ~half a day including verification. Risk: low-to-moderate, concentrated in the custom/on-prem
provider path.

## Findings

### F1 — `setRuntimeApiKey()` third argument changed type (breaking, the only compile error)

0.84.0: *"Changed `ModelRuntime.setRuntimeApiKey()` to accept auth cancellation options rather than catalog
refresh options. Call `refresh({ providers: [providerId], signal })` separately when remote freshness is
required."*

New signature is `setRuntimeApiKey(providerId, apiKey, options?: AuthOperationOptions)` where
`AuthOperationOptions = { signal?: AbortSignal }` (`pi-ai/dist/auth/types.d.ts:39`). Our `{ allowNetwork:
false }` is no longer a valid member — TypeScript will reject it, so this cannot slip through silently.

Two call sites, both in `agent-worker/src/agent-runner.ts`:
- `:1011` — the main parent-runtime key install
- `:828` — inside `ensureProviderAuthResolvable()` (the custom-provider registration fix)

**Change:** drop the third argument entirely. Do **not** add a `refresh()` call — we deliberately run the
parent runtime offline (`modelsPath: null`, `allowModelNetwork: false`) and drive it with an explicit
`model` object, so we never wanted a catalog refresh. This change actually removes an argument that existed
only to suppress behaviour we never wanted.

**Verify after upgrade:** confirm startup still performs no network catalog fetch. The offline guarantee now
rests solely on `allowModelNetwork: false` at `create()`. Read `synchronizeCredentialState` in
`model-runtime.js` (called at `:398`) and confirm it stays local when the runtime is offline.

### F2 — New `CredentialSynchronizationError` failure mode at our key-install site (should handle)

0.84.0 adds *"`CredentialSynchronizationError` for credential changes that commit successfully but fail to
synchronize local model state."* In 0.84.1, `setRuntimeApiKey` now routes through
`enqueueCredentialOperation` → `synchronizeCredentialState`, so it can throw where 0.82.1 could not.

That call sits on the critical path of **every incident** — an unhandled throw fails the investigation
before it starts, which is precisely the failure shape we just spent a cycle fixing for custom providers.
The error's own semantics say the credential *did* commit, so it is not fatal to us.

**Change:** wrap both `setRuntimeApiKey` calls; on `CredentialSynchronizationError`, log and continue.
Add a test asserting a run survives a throwing `setRuntimeApiKey`, mirroring the existing
`should survive a failing auth probe instead of breaking the run` test.

### F3 — Native `samplingParams` partially supersedes our `sampling.ts` (adopt, do not replace)

0.84.0 adds `samplingParams` to `Model` and `StreamOptions` (`pi-ai/dist/types.d.ts:114-117, 677-678`):
a free-form object merged verbatim into the request body after pi's own fields, so its keys win.

The scope limit is decisive — quoting the type doc: *"Only applied by OpenAI-compatible adapters
(completions, responses, Azure responses); other APIs ignore it."*

So it does **not** cover `anthropic-messages`, `google-generative-ai`, or `bedrock-converse-stream`, which
`sampling.ts` does. Keep `sampling.ts`. But adopt `samplingParams` for the OpenAI-compatible path, because
it closes a gap the `onPayload` hook structurally cannot:

- **Subagents inherit it.** `onPayload` lives on the parent session only — a documented limitation of the
  sampling feature. `samplingParams` set on the model entry in `<agentDir>/models.json` is read by child
  `pi` processes, so subagent turns finally honour the operator's settings on custom/OpenAI-compatible
  endpoints.
- It survives inside pi's own retry/compaction paths, which bypass the loop config.

**Change:** in `writeCustomProviderModelsJson()`, emit `samplingParams` built from the active
`LLMSettings`; in `resolveModel()`, attach `samplingParams` to the synthesized model for OpenAI-compatible
APIs. Then make `sampling.ts` skip `openai-completions`/`openai-responses` **only if** the model carries
`samplingParams`, so the two mechanisms never double-apply. Anthropic/Google/Bedrock keep the existing
mapping untouched.

Order matters: pi merges `StreamOptions.samplingParams` over `Model.samplingParams` per key, and both are
merged after pi's named fields — same "operator wins" semantics `sampling.ts` already implements.

### F4 — `compat.supportsFinishReason` for on-prem endpoints (adopt)

0.84.0: *"support for OpenAI-compatible streams that omit `finish_reason`, using
`compat.supportsFinishReason` to infer normal and tool-use stops when the stream ends."*

Directly relevant: the gcore install runs custom endpoints on what looks like vLLM/SGLang behind
`*.caas.k1.*.cloud.gcore.dev`, and the `custom` provider path is the one that has already bitten us twice.
A stream that omits `finish_reason` previously surfaced as an unmapped/aborted turn.

**Change:** consider defaulting `compat.supportsFinishReason: false` for synthesized `custom` specs in
`resolveModel()`. Gate this on evidence — check worker logs on gcore for truncated or unmapped stops
first. Do not set it blind; the default of `true` is correct for well-behaved endpoints.

### F5 — Raw provider stop reasons now surface as errors (behaviour change to watch)

0.83.0: *"raw provider stop reasons across Google, Anthropic, Amazon Bedrock, Mistral, and OpenAI streams;
**unmapped terminal reasons now surface as provider errors instead of successful stops**."*

`agent-runner.ts:1265` branches on `msg.stopReason === "error"` and `oneshot-llm.ts:136-139` on
`"error"`/`"aborted"`. Turns that previously completed silently-but-wrong may now arrive as errors. This is
an improvement in correctness but can look like a regression in incident success rate.

0.83.0 also adds a `"pending"` stop reason for partial streaming messages. Our one-shot path treats anything
that is not `error`/`aborted` as success and returns the text, so a `"pending"` result would be returned as
a complete answer. `complete()` should not produce it, but a defensive branch is cheap.

**Change:** no required code change; add a `"pending"` guard in `oneshot-llm.ts` and watch error rates on
the first deploy.

### F6 — `message_update` payload shrink does not affect us (no work)

0.84.0 removes the cumulative `message` and `assistantMessageEvent.partial` fields from JSON/RPC
`message_update` events. `handleSessionEvent` (`agent-runner.ts:1420-1440`) already consumes **deltas only**
(`assistantEvent.delta`, `thinking_delta`), which is exactly what the migration note prescribes. Streaming
to Slack and the UI is unaffected.

Cosmetic only: the test mock in `tests/agent-runner.test.ts` still sets a `partial: {}` field that no longer
exists. Drop it so the mock does not describe a shape pi no longer emits.

### F7 — Session/harness rewrite does not reach us (no work)

0.84.0's v4 lane-based `Session`/`SessionStorage`/`SessionRepo`, the removal of "legacy JSONL and in-memory
repository APIs", and the required `FileSystem.renameFile()` are all **pi-agent-core harness** concerns. We
use `SessionManager` from pi-coding-agent, and all three statics we call still exist in 0.84.1
(`session-manager.d.ts:318/331/333`). We implement no custom `FileSystem` and no harness.

Confirm at upgrade that session JSONL exports still land in the worker work dir (post-mortem analysis
depends on them), since atomic JSONL publication changed underneath.

### F8 — TypeBox 1.3.7 removals do not affect us (no work)

0.83.0 removes `Type.Base`, `Type.Awaited`, `Type.Promise`, `Type.AsyncIterator`, `Type.Iterator`,
`Type.Options`, `Value.Mutate`. `gateway-tools.ts:9` imports only `Type` and `Static`; grep confirms none of
the removed APIs appear anywhere in the worker or gateway. The same release *fixes* compiled validation of
nullable array tool arguments, which is a free win for `gateway_call` schemas.

### F9 — Other breaking changes that do not apply (no work)

- `ModelsStreamTransforms` → `ModelsRequestTransforms`: we never reference it.
- `ModelRegistry.getApiKeyAndHeaders()` / `refresh()` signature changes: we use `ModelRuntime`, and grep
  finds `ModelRegistry` only in stale comments (`agent-runner.ts:999, 1026` — worth correcting).
- Extension provider `context.store` → `context.stored`/`publish()`: we register providers through
  `ModelRuntime.registerProvider`, not `refreshModels`, and pass a static model list.
- OAuth `refreshToken(credentials, signal)`: we use API keys only.
- Remote-session `SessionMetadata`: experimental APIs we do not consume.

### F10 — Free wins arriving with the bump (no work)

- OpenAI-compatible tool calls no longer lose function arguments on malformed deltas containing an empty
  `custom` object (0.83.0) — a real hazard for `gateway_call` on custom endpoints.
- Z.AI output limits no longer sent through an unsupported parameter (0.83.0) — the gcore install runs
  GLM-4.7, a Z.AI model.
- Amazon Bedrock explicit profiles no longer overridden by ambient AWS keys (0.83.0).
- llama.cpp token usage / context accounting fixed (0.83.0) — improves `tokens_used` fidelity on on-prem.
- `Agent.reset()` no longer clears state during active runs (0.84.1).
- Structured Bedrock failure diagnostics with HTTP status and AWS request id (0.84.0).

### F11 — Optional adoptions, deliberately deferred

- **`pi auth check`** (0.84.1) — a credential preflight that would have diagnosed the `custom` provider
  auth bug in seconds. Worth a follow-up: expose it as an operator "Test connection" button on the LLM
  settings form. Out of scope for the upgrade itself.
- **New providers**: Baseten (`BASETEN_API_KEY`, 0.84.0) and Qwen Token Plan Individual (0.84.1). Adding
  either means touching `LLMProvider` in Go, the worker's provider union, `PROVIDER_API_KEY_ENV_VARS`,
  `llmModelSuggestions.ts`, and `apiMap` in `resolveModel`. Only do it on demand.
- **`AgentOptions.shouldStopAfterTurn`** (0.84.0) — a graceful stop-after-turn that is a better fit than
  our current abort path for superseded runs. Evaluate separately.
- **Per-request `fetch` injection** (0.83.0) — could replace the global proxy env-var mutation in
  `proxy.ts` with per-request proxying, removing a process-global side effect. Attractive but a separate
  refactor.
- **`AGENTS.override.md`** (0.84.0) — per-directory context override. We generate `AGENTS.md`; be aware
  operators can now shadow it per directory.
- Fullscreen TUI, Mermaid/LaTeX rendering, scrollbars, prompt history: interactive-only, irrelevant headless.

## Work Plan

**Phase 1 — Mechanical bump.** Update the three `@earendil-works/*` deps and `pi-subagents` to 0.45.1 in
`agent-worker/package.json`, `npm install`, `npx tsc --noEmit`. Expect exactly the two `setRuntimeApiKey`
errors from F1 and nothing else; any additional error means this analysis missed something and should be
investigated before proceeding.

**Phase 2 — Required fixes.** F1 (drop third arg, both sites) and F2 (tolerate
`CredentialSynchronizationError`). Update the stale `ModelRegistry` comments. Drop the dead `partial: {}`
from the test mock (F6).

**Phase 3 — Adoption.** F3 (`samplingParams` for OpenAI-compatible, including the subagent path) then F5's
`"pending"` guard. Hold F4 until gcore logs justify it.

**Phase 4 — Verification.** `make test-agent` (416 tests today), `make test`, `make test-web`. Then the
checks the type system cannot make:
1. Offline startup — no network catalog fetch (F1).
2. A real investigation on **Anthropic** (built-in provider, native thinking).
3. A real investigation on **custom** (gcore Deepseek/GLM) — the path that broke twice; confirm auth
   resolves, streaming reaches Slack, and subagents authenticate.
4. A subagent invocation, confirming `samplingParams` reaches the child.
5. Session JSONL export still written (F7).
6. One-shot calls: title generation and alert extraction.

**Phase 5 — Rollout.** Same path as the sampling feature: push to `main`, let CI publish `main-<sha>`, then
re-pin `/opt/akmatori/.env` on gcore (`AKMATORI_VERSION=main-<sha>`) and `docker compose pull && up -d`.
Rollback is restoring the previous pin. Note gcore currently sits on `main-8d51705`, off the `:latest`
release stream — a `v*` tag is still needed to move other installs.

## Changes Made

Phases 1–4 executed on 2026-08-10. Phase 5 (rollout) pending.

### agent-worker/package.json
`@earendil-works/pi-coding-agent`, `pi-ai`, `pi-agent-core` → `^0.84.1`; `pi-subagents` → `^0.45.1`.

### agent-worker/src/agent-runner.ts
- F1: dropped the `{ allowNetwork: false }` third argument from both `setRuntimeApiKey` call sites.
  `ProviderRegisteringRuntime` updated to mirror pi's new `{ signal?: AbortSignal }` — the stale local
  shape was why only one of the two sites produced a compile error.
- F2: new `setRuntimeApiKeyTolerantly()` swallows `CredentialSynchronizationError` (matched by `name`,
  which pi sets explicitly; `instanceof` is unusable because the tests mock the package root). All other
  errors still propagate.
- F3: extracted the inline `apiMap` to module-scope `PROVIDER_API_MAP` and added
  `providerUsesOpenAICompatibleApi()`. `writeCustomProviderModelsJson()` now writes `samplingParams` onto
  the managed model entry so **child subagent processes** inherit operator sampling settings.
- Corrected stale `ModelRegistry`/pi-0.81 comments.

### agent-worker/src/sampling.ts
Added `OPENAI_COMPATIBLE_APIS` and `toOpenAISamplingParams()`. `max_tokens` is deliberately excluded from
`samplingParams` (verbatim merge would send `max_tokens` to the Responses API, which wants
`max_output_tokens`); output length stays with the existing per-API mapping.

The parent-side `onPayload` hook is unchanged: pi merges `samplingParams` into the body *before* the hook
runs, so identical values simply overwrite themselves. No double-apply hazard, and non-OpenAI adapters keep
the only mechanism that works for them.

### agent-worker/src/oneshot-llm.ts
F5: reject `"pending"` (0.83.0) and `"deferred"` (0.84.0) stop reasons instead of returning a non-final
message as a finished answer, which would silently corrupt an incident title or an alert extraction.

### web/src/components/settings/llmModelSuggestions.ts
Added the three gpt-5.6 variants for `openai` and `openrouter` (see gpt-5.6 note below); demoted the
gpt-5.5 labels. Test expectations in `LLMSettingsSection.test.ts` updated accordingly.

### Verification performed
- Worker 422 tests, web 176 tests pass. Go unchanged (2 pre-existing `TestHandleIncidents_Trend*` failures
  that also fail on a clean `origin/main`).
- Typecheck after the bump produced **exactly** the predicted `setRuntimeApiKey` error and nothing else.
- Offline guarantee re-verified against the real SDK: `ModelRuntime.create({allowModelNetwork:false})` +
  two `setRuntimeApiKey` calls make **zero** `fetch` calls (F1's residual risk).
- Custom-provider auth re-verified against the real 0.84.1 SDK: `getAuth` `undefined` → `RESOLVED` with the
  correct key after `ensureProviderAuthResolvable()`.

### Not done (deliberate)
F4 (`compat.supportsFinishReason`) — still gated on gcore log evidence, per the finding. All of F11.

### gpt-5.6 — already supported, was not discoverable
Not an upgrade item: `gpt-5.6-luna` / `-sol` / `-terra` were already in pi **0.82.1**'s bundled catalog and
resolved with full metadata (272k context, 128k output, `thinkingLevelMap` through `max`). There is no plain
`gpt-5.6` id. The gap was purely the UI picker, which stopped at gpt-5.5. Ordering follows catalogue pricing
(sol $5/$30, terra $2/$12, luna $0.20/$1.20 per M) — the only capability signal the catalog exposes.

Note the parent runtime uses `allowModelNetwork: false` with the bundled catalog, so **new models only ever
arrive with a pi version bump**, never at runtime.

`orchestrator.ts`'s hardcoded fallback model is still `"gpt-5.5"`; it only fires when the API sends no model
at all, and was left alone as out of scope.

## Risks

1. **The `custom` provider path is the fragile one.** It broke on the 0.82.1 upgrade
   (`registerProvider`) and it is where `samplingParams`, `supportsFinishReason`, and the tool-call-argument
   fix all land. Test it explicitly on gcore rather than trusting unit tests — the last regression was
   invisible to the whole suite.
2. **Silent behaviour change from F5.** Unmapped stop reasons becoming errors may raise the observed
   failure rate without any regression in our code. Compare incident error rates before and after.
3. **`samplingParams` double-application.** If `sampling.ts` and the model entry both set a key for an
   OpenAI-compatible model the values must agree; the F3 skip-condition exists to prevent divergence. Cover
   it with a test.
4. **pi-subagents jumps nine minor versions** (0.36 → 0.45) with its own unreviewed changelog. Its peers
   are `*`/`>=0.80.0` so nothing forces the bump — if subagents misbehave, pin it back and upgrade
   separately.
